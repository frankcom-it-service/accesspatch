# Limitations

## Current Limitations

- A controlled React checkout fixture and predefined Playwright journey exist; this fixture is not the AccessPatch product and supports only the seeded local scenario.
- Phase 1B can collect schema-valid evidence and obtain a deterministically constrained repair plan only for the two seeded findings. Committed Phase 1C code can generate and validate an isolated two-file patch and repaired replay for those findings. Committed Phase 2A code packages that reviewed evidence into the fixed canonical bundle. Arbitrary-repository inspection, retained patch application, rollback, broader proof formats, and the complete product workflow are **NOT YET IMPLEMENTED**.
- Dedicated-project authentication and one real `gpt-5.6-sol` Phase 1B planning call are verified. Broader output quality, latency, cost profile, failure modes, and supported findings remain **NOT YET VERIFIED**. Codex credits do not automatically provide OpenAI API credits.
- Only the controlled build, smoke, keyboard-baseline, and checkout axe results are verified; product-level accessibility, security, performance, compatibility, and usability remain **NOT YET VERIFIED**.
- The repository model is private judging with no open-source project license. The canonical private repository exists and both required read invitations remain pending; accepted judging access, an independent judge clone, and a hosted application demo remain unverified. The public `2:49` YouTube submission video and its selectable corrected English captions were verified by the project owner in a logged-out/incognito browser. Core requirements were checked on 2026-07-15, but the official Rules-page body appears stale and the final applicable rules remain an open risk.
- Support beyond the controlled React fixture and Chromium-only test scope remains `OPEN`; committed Phase 3B evidence verifies one fresh clone on Debian GNU/Linux 13 x86_64, but other operating systems, browser configurations, and the Playwright-managed Chromium fallback remain unverified. Only two finding types and two safe-fix classes are currently allowed.
- The generated static report passed automated Chromium axe smokes, but it has not received complete accessibility review. Phase 2C commits an independently reviewed tracked byte-identical sample, Phase 3A integrates it into the committed judge workflow, and Phase 3B verifies that path in one clean Linux clone.
- The committed Phase 2B WCAG 2.2 mapping covers only three criteria for the two controlled findings. It does not assess other criteria, the whole page, the complete process, accessibility-supported usage, or WCAG conformance. Criterion expansion requires separate official-source review.
- Phase 3A’s workflow is verified locally, and Phase 3B verified the committed workflow in one fresh Debian GNU/Linux 13 x86_64 clone. Broader-platform and alternate-browser behavior remain unverified. The first lifetime run failed on a corrected ignored-run test dependency; the second local run and third lifetime clean-clone run passed. This does not establish arbitrary-repository support.
- The private repository and explicit submission references exist, but both read invitations remain pending. No accepted judging access, independent clone, server, subdomain, deployment, public page, or no-cost access state has been verified.
- Phase 5A is clean-clone verified and merged into `main` by strict fast-forward from reviewed HEAD `e7701516f07c204c8ba5792dcf2c100c9b508222`; the local feature branch remains retained but unpublished. Its 17-stage acceptance covers Debian GNU/Linux 13 x86_64, Node `v24.18.0`, pnpm `11.13.0`, Git `2.47.3`, and Chromium `148.0.7778.178`. It supports exactly one controlled mutation class on fixture `demo-checkout-controlled-v1`, bound to one approved four-file hash: `aria-hidden="true"` on one existing focusable checkout button in a disposable copy. Other platforms, fixture versions, browser paths, and repositories are rejected or unverified rather than inferred. It is not fuzzing, broad mutation testing, arbitrary JSX/HTML rewriting, full WCAG coverage, certification, legal compliance verification, retained patch application, fallback, rollback, or a replacement for human review.

## Permanent Claim Boundaries

Even if implemented, AccessPatch cannot claim complete accessibility, provide WCAG certification, provide BFSG or EAA legal assurance, find every accessibility issue, or replace disabled-user testing and qualified human review. Automated and model-assisted results can be incomplete or incorrect and require review.
